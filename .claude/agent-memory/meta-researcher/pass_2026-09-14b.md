**Recommended, pending meta-architect action:**

1. **`.claude/hooks/post-edit.mjs`'s `isWebSrc` branch should add `npm run typecheck:scripts`
   alongside its existing `npm run typecheck:web`.** Source: NOT platform docs — a real incident
   recorded in `.claude/agent-memory/web-developer/refactor_powerup_optimizer_4stage_extraction.md`
   (written 2026-09-14, this session's own fresh evidence). During the PowerUpOptimizerView
   extraction, `blockedCandidateSentence` moved out of `PowerUpOptimizerView.tsx`; 4 of 5 import
   sites were updated but `scripts/run-scenario.ts`'s import was missed. `npm run typecheck:web`
   (what the hook currently runs on every `packages/web/src/**` edit) stayed clean because its
   `tsconfig.json` project root never includes `scripts/` as an entry point — the break was a pure
   ESM runtime error, only caught when `test:scripts` executed the CLI under `tsx`. Confirmed by
   reading `tsconfig.scripts.json` directly: its own header comment states it deliberately reaches
   into `packages/web/src`'s `.tsx` View files' exported constants/functions
   *because* `scripts/run-scenario.ts` imports them — i.e. `typecheck:scripts` is already the
   exact cheap, existing mechanism the incident needed; it just isn't wired into the hook that
   fires on the file class that broke it. The engine-developer memory note itself already says so
   explicitly: "even though `npm run typecheck` ... would also have caught it as a TS2305 if run."
   Recommending the narrower `typecheck:scripts` addition rather than swapping to the full 4-way
   `typecheck` — `typecheck:engine`/`typecheck:engine-test` check `packages/engine`, which a
   web-only edit cannot break, so including them would add tsc runtime with zero marginal
   detection for this file class. **Cost**: a hook script, so no context-window cost at all; the
   only ongoing price is one more bounded, offline `tsc -p tsconfig.scripts.json` invocation each
   time a `packages/web/src/**/*.{ts,tsx}` file is edited, on top of the `typecheck:web` the hook
   already runs synchronously. Nothing to retire — this is additive to an existing branch, not a
   new hook.

**Confirmed non-finding (the second lead named in this pass's invocation), reported per the
"say plainly" instruction rather than silently dropped:**
`check-scenario-roundtrip.mjs`'s hardcoded `TABS` table (`[label, file, interfaceName, file,
toFn, fromFn]` per tab) does NOT silently skip a tab when a row goes stale after a file move —
read `runCli()` directly (`scripts/check-scenario-roundtrip.mjs` lines 173-211): a missing
`toFn`/`fromFn` or a missing `interfaceName` both `console.error` a named "(renamed or moved?)"
message, increment `failures`, and the CLI `process.exit(1)`s at the end if `failures > 0`. A
deleted *file* (as opposed to a moved function inside a surviving file) would throw an uncaught
`fs.readFileSync` ENOENT, which also exits non-zero, just with an uglier stack trace instead of
the clean message. Either way, CI/the `check` gate fails loudly; nothing passes silently. This
was borne out in practice the same day: the PowerUpOptimizerView refactor DID move the round-trip
functions was anticipated by the task itself, the row was updated, and the checker's own
field-count assertion (155/155) was used as a stage-by-stage correctness check, never a soft
failure. No hook/script change to propose here — the existing design already the right answer to
the question posed.
