`packages/web/vitest.config.ts` deliberately runs with `environment: "node"` and carries an explicit comment: no component rendering, no DOM, no React Testing Library — UI-behavior verification is the manual/browser checklist, not a component test suite. Neither `jsdom`/`happy-dom` nor `@testing-library/react` are installed anywhere in the repo (checked `package.json` at both root and `packages/web`, and `node_modules` directly — confirmed absent, not just unconfigured).

That policy is about *component rendering* (mounting into a real or simulated DOM), not about testing a class component's own methods. **`TabErrorBoundary` (`packages/web/src/TabErrorBoundary.tsx`) is a plain ES class extending React's `Component`, and its `render()` method is just a function returning plain data** — React elements are `{ type, props, ... }` object literals, not DOM nodes. Wrote `TabErrorBoundary.test.tsx` (co-located, matches every other `*.test.ts(x)` in this package) that:

1. Constructs the class directly — `new TabErrorBoundary({ tabLabel, onResetTab, children })` — no `ReactDOM.render`/`createRoot` involved. React's `Component` constructor has no DOM dependency; it just sets `this.props`.
2. Calls `TabErrorBoundary.getDerivedStateFromError(err)` directly (a static method) and asserts its return shape.
3. Sets `instance.state` directly to that return value (mirroring what React's reconciler does after `getDerivedStateFromError` fires — this is the one honest simplification: no real "a child threw during an actual render pass," since there's no reconciler here to produce one) and calls `instance.render()`.
4. The result is a React element whose `.type` is the (unexported) `TabCrashFallback` function component — **since it's just a function, call it directly** (`fallback.type(fallback.props)`) to get ITS element tree one level deeper, with zero extra imports needed (it was never exported, and doesn't need to be).
5. A small recursive `findElement`/`findText` walker (own to the test file, ~15 lines, not a shared helper — this is the only file that needs it) searches that plain object tree for the `<button>` and asserts `button.props.onClick === onResetTab` — the exact callback **reference**, not a copy or a no-op. This is actually a STRONGER assertion than an HTML-string render (`react-dom/server`'s `renderToStaticMarkup`, also considered) could give, since HTML output strips event handlers entirely — reference equality on the raw element tree is the only way to prove the wiring without a real DOM.

Result: 4 tests (`getDerivedStateFromError` captures the error / renders children unchanged when nothing thrown / `componentDidCatch` logs via `console.error` spy, not swallowed / full fallback-render with button wiring), zero new dependencies, zero `vitest.config.ts` changes, ~90 lines. Verified with a throwaway scratch test first (`npx vitest run` directly, deleted after) before committing to the real file, to confirm the technique actually works in this environment rather than assuming it would.

**When this pattern generalizes:** any class component (or, via the same "call the function directly" trick, a *function* component) whose logic is what needs testing, not its actual DOM output/interactivity/event bubbling/CSS. It stops working the moment a test needs `useEffect`/`useState` hook timing, real event dispatch, or anything DOM-shaped (`getBoundingClientRect`, focus, etc.) — that's genuinely `@testing-library/react` + `jsdom` territory, and this project still has none of that, deliberately.

**Why this matters more than an average coverage gap** (coordinator's framing, worth keeping): an error boundary is a safety net for crashes nobody anticipated — a botched refactor, a dropped wrapper in `App.tsx`, a lazy-chunk change — and it could break silently, with the first sign being a user staring at a white screen, the exact failure it exists to prevent. "This is hard to test with the tools on hand" is not the same conclusion as "this is untestable" — check for a different seam (unit vs. e2e; direct class construction; an extracted pure function, e.g. `dodgeExecutionErrorLeader.ts`'s precedent) before concluding a component has no honest test.
