## Findings

### 0. Ranking-flip marker reports the wrong crossing — HIGH
`DamageOverTimeChart.tsx` scans for a sign flip in the two candidates' delta and `break`s on the
**first** one. `finalLeader` directly below is computed independently, from the final
totals. When the lead flips twice — one candidate briefly overtakes, the other
retakes it for good — the green marker and its caveat sentence describe the first,
non-decisive flip while `finalLeader` names the winner of the second. The marker and its
own sentence contradict each other.

This is the product's headline output. CLAUDE.md: "The product's headline output is
*where that ranking flips*, not which name is on top."

Reproduces on the zero-query-param default Comparator load (Kartana vs Rayquaza):
own-damage 5s 24/27, 6s 66/27, 7s 74/155 -> delta -3, +39, -81. Marked "~5.4s"
(the first flip); the decisive second flip goes unmarked.

**Fixed.** The scan now retains the last flip and derives `finalLeader` from that same flip.
Verified in the browser: marker and sentence both report ~7.0s / Rayquaza (was ~5.4s).

### 0b. Form ingestion keyed on stats only, so type-distinct forms are still wrong — HIGH
Follow-on defect from my own spec for finding 1: I specified "base stats differ" as the
discriminator for ingesting a form. It must be **stats OR types differ**.

Several real forms share their base form's stat line but have completely different
typing, so they are still substituted with the wrong types:

- **Hisuian Sneasel** (fighting/poison) modelled as base Sneasel (dark/ice) — and it is a
  CURRENTLY ACTIVE 3-star raid boss.
- Hisuian Voltorb (electric/grass) as Voltorb (electric).
- Galarian Darmanitan Standard (ice) as Darmanitan (fire).

Measured error against Hisuian Sneasel at L40 15/15/15:

| attacker | TDO before fix | TDO after fix |
| :--- | ---: | ---: |
| Metagross | 715 | **1276** |
| Rayquaza | 224 | 958 |
| Gengar | 261 | 730 |
| Machamp | 778 | 347 |
| Kartana | 530 | 296 |

**The ranking inverted.** Before the fix Machamp (778) ranked above Metagross (715); after it,
Metagross (1276) leads Machamp (347) by 3.7x. Wrong typing was not just scaling numbers, it was
reordering which attacker wins — the exact output this product exists to produce.

(An earlier estimate in this file put Metagross at 1913. That was a synthetic species carrying
base Sneasel's moveset with Hisuian typing; the real ingested species has its own moves, so 1276
is the true figure. Direction and severity unchanged.)

Type effectiveness swings results far harder than the stat lines do, so this is the more
damaging half of finding 1 and is very likely a large part of the long-standing
"numbers look wrong" reports.

**Fixed.** The qualifying condition is now stats OR types. 63 type-only forms ingested; zero
active raids remain flagged approximate.

### 1. 52 mechanically-distinct forms missing from the roster — MEDIUM (latent HIGH)
Exact stats exist in `data/raw/pokemon_stats.json` but never reach
`data/normalized/species.json`. When such a form becomes a raid boss the pipeline
substitutes the **base form** and flags `isApproximate`.

Live impact today is small: Hisuian Lilligant (214/155 used vs 208/159 real, ~0.7%
TDO error) and Hisuian Sneasel (identical stats, 0% error).

Latent impact is severe — these are all real raid bosses:
- Calyrex Shadow Rider 324/194 vs base Calyrex 162/162 (**100% attack error**)
- Deoxys Attack 414/46 vs base 345/115
- Galarian Articuno 250/197 vs base 192/236
- Origin Dialga/Palkia, Black/White Kyurem, Necrozma Dusk Mane/Dawn Wings/Ultra

Also the root cause of the 44 unresolved names in the Bulbapedia historical backfill.

**Fixed.** 83 stat-distinct + 63 type-distinct forms ingested (1092 -> 1238 species). Cosmetic
forms still excluded. See finding 0b — the first pass keyed on stats alone and had to be widened.

### 2. Pokebattler cross-check reports false disagreements — MEDIUM
`RAID_LEVEL_MEGA` is a rotation **pool**, not a live list: it contains
`SKARMORY_MEGA`, whose rotation demonstrably ended (that is why Mega Skarmory
vanished from `species.json` earlier), plus Mega Raichu X/Y which are not live.
This makes the new cross-check report ~11 phantom Mega disagreements every run.

Verified genuinely current and exactly matching ScrapedDuck: `RAID_LEVEL_1`, `_3`,
`_5`, `_1_SHADOW`, `_3_SHADOW`, `_5_SHADOW`. `RAID_LEVEL_UNSET` (2192 entries) is a
full-Pokédex catalog and is already correctly excluded.

**Fixed.** Mega/primal excluded symmetrically from BOTH sides (excluding only one side just
relocated the phantom) and reported on a separate advisory line. Down to 1 real disagreement.

Residual real difference after that: Shadow Grubbin (ScrapedDuck only) — likely
genuine lag on Pokebattler's side, worth watching rather than acting on.

### 2b. Accumulate-only history preserves stale mis-resolutions — MEDIUM
Surfaced while verifying the type-forms fix in the live app. `raidHistory.json` never revisits a
row once written, so a mapping recorded before a resolution fix survives forever:

```
speciesId=sneasel            raidName="Hisuian Sneasel"    source=live-feed   <- stale
speciesId=sneasel-hisuian    raidName="Hisuian Sneasel"    source=live-feed   <- correct
speciesId=lilligant          raidName="Hisuian Lilligant"  source=live-feed   <- stale
speciesId=lilligant-hisuian  raidName="Hisuian Lilligant"  source=live-feed   <- correct
```

Effect: Hisuian Sneasel renders TWICE in the Species Report — the correct active row, plus a
`PAST`-badged row that is really base Sneasel (dark/ice, base stats) shown under the Hisuian
name. The wrong-typing bug of finding 0b, reintroduced through the history file.

Found by comparing each row's `raidName` against its resolved species' `name`: exactly 5
disagree, 4 being these two pairs. The 5th (`furfrou-dandy` / "Furfrou") is benign — a generic
archive name resolving to a specific form, not a mis-resolution.

The general lesson: accumulate-only should mean "never lose a recorded encounter", not "never
correct a bad id".

**Fixed.** Rows are re-resolved each sync and merged (oldest `firstSeenAt`, strongest `source`,
any `eraHp`) rather than duplicated; unresolvable rows are left untouched, and the benign
generic-vs-specific case is explicitly excluded. Count went 604 -> 603, not 602: removing the two
stale rows also unmasked base Sneasel's own genuine 1-Star appearance (`eraHp` 1800), which the
wrong live-feed row at that id had been outranking and hiding the whole time. The fix also had to
clear the stale `lastKnownRaidTier` that would otherwise have regenerated the phantom row on the
next sync.

### 2c. Historical rows use today attack/defense multiplier, not their era's — CLOSED (won't fix)
Niantic's 2020-08-27 merge folded tier 2 into 1 and tier 4 into 3. A species whose recorded
appearance was old tier 4 is therefore simulated with 3-Star's 0.73 attack/defense multiplier,
where the real four-star value was **0.79** — sourced from Bulbapedia's difficulty table, which
lists Community Day raids (explicitly four-star) at 0.79 and describes Mega raids as
"equivalent to a four-star raid" at the same 0.79.

Scope: ~35 species, ~8% error on the boss's attack and defense. The old tier-2 cohort (~38
species) has no sourceable multiplier at all — Bulbapedia's table only lists currently-live
tiers, so there is nothing to correct it to.

Note this is a DIFFERENT quantity from era HP (finding 0/1). Boss HP is not an input to the
Species Report simulation at all (see finding 3's neighbours and `simulate.ts`, which has zero
boss-HP references) — the attack/defense multiplier genuinely is. So this is the only era
inaccuracy that actually moves Species Report numbers.

**Decision (user, 2026-09-08): not fixing.** An 8% term on 35 species does not justify an engine
change, and half the affected population cannot be corrected honestly anyway. Recorded here so it
is not rediscovered and re-litigated as a new finding.

### 3. Attack and Defense are floored — CLOSED (won't fix)
`effectiveStat` floors all three stats. In GO only HP is an integer; Atk/Def are used
unrounded. Effect: ±1 damage on ~1% of matchups, not systematically biased (flooring
defence raises damage, flooring attack lowers it). Fixing it would touch every test.

**Decision (user, 2026-09-08): accepted as-is.** A known engine-precision limitation, not a bug
to chase.

### 4. `STRUGGLE` has `energyCost: 0` — CLOSED (not a defect)
42 species carry it as their only charged move. The zero comes from pogoapi upstream
(`energy_delta: 0`), faithfully propagated — not our bug. All 42 are weak species where
the practical effect is negligible.

**Resolved (2026-09-08): pogoapi is CORRECT; this was never a defect.** Struggle has two
distinct energy costs and Bulbapedia carries them as separate fields, verified by direct
`action=raw` fetch of `Struggle_(move)`:

```
|energy=0            <- raids / gyms
|energy_trainer=100  <- trainer battles (PvP)
```

Its patch log shows the PvE value moved 20 -> 0 -> 33 -> 0 during 2017 and has been 0 since.
The 100 figure is real but is the PvP number; this project models raids/gyms only and has no
PvP tab, so a free-firing Struggle on those 42 species is a faithful simulation. The move's
users list in that wikitext matches our 42 species exactly.

If a PvP tab is ever built it needs a SEPARATE energy field, not an override of the raid value —
both numbers are simultaneously true.

### 5. Dodge silently saturates below the boss's charged-move duration — IN PROGRESS
Setting boss charged frequency under that move's own duration (e.g. 2s vs Stone Edge's
2.5s) makes dodge worth exactly 0. Physically sensible, but the UI allows a minimum of
1s where the setting quietly stops mattering.

**Root cause:** nothing constrains the sampled interval to be at least the charged move's own
duration, so a boss can be asked to fire a 2.5s move every 2s. The moves overlap, the attacker
never gets a gap, and dodge is worth exactly nothing. Dodge starts mattering precisely at the
move duration, which is the tell.

**Being fixed (user asked for a real fix, 2026-09-08):** clamp the sampled interval to the
physical minimum and expose the effective value so a silently-adjusted assumption is visible —
the same honesty convention as the "approximate" badge.

### 6. Team Raid never explains "approximate" — FIXED
The other four tabs all carry the caveat; Team Raid's picker showed the badge with no explanation
anywhere on the tab.

**Fixed.** Added to Team Raid's Known Caveats. User confirmed the "approximate" label itself is
the right treatment (2026-09-08) — the gap was the missing explanation, not the badge.
